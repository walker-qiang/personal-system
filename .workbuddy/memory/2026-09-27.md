## DeepSeek 400 根因修复 + app 级整体联调（personal-agent × personal-os）

### 400 "No tool output found for tool call" 的真正根因（不是 Commander）
- 表象：DeepSeek Responses API 要求每个 `function_call` 配对 `function_call_output`。
- 真实根因在 `src/matrix/llm/truncate.py::truncate_messages`：`budget = max_tokens - reserve_tokens - estimate_tokens(system_prompt)`。
  agent 的 system prompt（注入了 guidelines/lessons/data index）**本身就超过 4000 token 预算** → budget ≤ 0 →
  历史被压成**单条消息** → 工具结果全部丢失 → 模型看不到结果就重复同一个调用（实测 7 轮 → `maximum turns exceeded`），
  且请求里出现无配对的 `function_call` → 400。
- 修复（两处）：
  1. `truncate.py`：system prompt 最多只占用一半消息预算（`max(message_budget - system_tokens, message_budget // 2)`）；
     budget ≤ 0 时不再塌缩成 1 条，改为保留最近 6 条的 pair-safe 窗口（新增 `_recent_window`）；
     兜底：若裁剪结果只剩 1 条而输入 >1 条，同样回退到 `_recent_window`。
  2. `llm/deepseek.py`：发送前补配对（新增 `_ensure_tool_call_outputs`），缺失输出注入占位 `{"error": "tool produced no output"}`
     并打 WARNING。这是**兜底**，不是主修复——主修复是上面的预算 bug。
- 效果：修复前日志 7 次 `missing output` 警告 + 循环超限；修复后同类警告消失，单次 chat 流从 44 事件涨到 ~1500-2100 行（上下文完整）。

### app 级整体联调（跨两个仓库，非单测）

## App 顶栏「AI 模型异常：DeepSeek response message content is empty」修复

- 链路：App `AppModel.checkModelConnectivity()` → `api.getAgentHealth(probe:true)`

  1. `chat/_service.py::probe_llm` 探针预算 16 → **512**（主聊天是 8192，本来就没问题）。
  2. `llm/deepseek.py::complete()` 空内容时抛出**可诊断错误**：带上 `max_output_tokens`、`status=incomplete(reason)`、
     实际 output 类型（如 `reasoning`），并提示"推理模型吃掉预算时调大 max_tokens"。

### 2) 定位并修复「vault 写入永久 409」的真因（personal-os commit e573027）
- 现象：DELETE /memory/{key} 返回 503 `assetstore lock is already held`。
- 取证：`lsof -p 80011 -a -d 13` 显示锁文件仍被 API 打开；`lsof | grep 0x95d3…`（管道另一端）
  揪出 **`ssh 81784 … git-upload-pack 'walker-qiang/personal-assets.git'`**，cwd=personal-assets，
  fd 6 开着 `/dev/tty`，TCP 到 GitHub ESTABLISHED，已挂 90 分钟 → 22:07:48 那次 `memory.sync`
  的 `git fetch` 卡在 host-key 确认上，`WithLock` 因此永不释放。
- `kill -TERM 81784` 后锁文件立刻消失（`Release()` 正常执行），证明是"goroutine 卡在 git"而非"fd 泄漏"。
- 修复：`runGit` 加 `GIT_TERMINAL_PROMPT=0` + 默认 `GIT_SSH_COMMAND`（`BatchMode=yes`、`ConnectTimeout=15`、
  keepalive）+ 120s 超时（`PERSONAL_OS_GIT_TIMEOUT_SEC`）；`setEnv` 用替换而非追加，避免重复项。
  新增 `packages/assetstore/git_env_test.go`（含"git 永不返回时必须超时"的用例）。
- 效果：同样失败的调用从"挂 90 分钟"变成 **1–3 秒内明确报错**。

### 3) 剩余阻塞（下次继续）：API 读不到 ~/.ssh
- 重启后的 API（pid 90761）报 `hostkeys_foreach failed for /Users/liqiang/.ssh/known_hosts: Operation not permitted`
  → `Host key verification failed`。原因：**从 WorkBuddy 会话启动的进程继承沙箱**（fd 3/4 是
  `~/.workbuddy/logs/sandbox/20260927/sandbox_59719*.log`），沙箱不允许读 `~/.ssh`。
- 因此 `DELETE /memory/{key}?hard=true` 仍失败（5 条 e2e 偏好还在 runtime SQLite：
  `report_bullet_count`、`report_format_table`、`hs300_etf_dca`、`report_max_length`、`report_language`）。
  **注意 DELETE 会先 `sync_memory_profile` 写 vault，写失败就 503 且不删本地键**（顺序问题，值得后续改成先删本地）。
- 下次最省事的解法：**用户在自己的 Terminal 执行 `cd ~/code/personal-system/personal-os && ./tools/dev`**
  （脱离沙箱 → 能读 `~/.ssh` → vault 写入可用），然后再删这 5 条键；
  或者接受"runtime 里多 5 条偏好"，vault 文件本身是干净的（8 条）。
